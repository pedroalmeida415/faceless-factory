# Feature Clean Architecture Boundaries

Accepted. Feature modules should be organized around `domain`, `application`, and `infra` boundaries: `domain` contains business rules, domain errors, value objects, domain services, and business protocols with Effect as a first-class foundation for typed services, recoverable failures, interruption, and dependency requirements; `application` contains use cases, orchestration, and the ports/contracts those use cases need; and `infra` implements application ports using external libraries, SDKs, databases, queues, and framework-specific mechanisms. Global technical capabilities belong in `src/core`, split into `core/application` ports and `core/infra` adapters; `core` is not a home for feature domain concepts, and `core/application` ports should use generic capability language rather than feature nouns such as Runtime Task, Workflow Asset, or Task Status Event. Core application ports should be broad but cohesive capabilities, such as database, job queue, blob store, pub/sub, telemetry, AI generation, and payment gateway, rather than feature-specific services or a single god service. The dependency direction is `feature application -> feature domain`, `feature infra -> feature application + core/application`, `core/infra -> core/application`, and `main -> feature application + feature infra + core/application + core/infra`; feature infra may depend on core application ports but not core infra implementations. Feature application should normally depend on feature-owned ports expressed in business/use-case language; feature ports should be deep cohesive transaction or use-case capabilities, not shallow CRUD repositories, and feature infra translates those ports to core capabilities. Feature infra should not bypass application by implementing domain ports directly. Application code should depend on domain and application-owned ports, not on shared service implementations such as database, queue, storage, telemetry, provider, or payment services. Deterministic in-memory domain rules may remain plain functions when Effect adds no leverage. Root composition belongs in `src/main`, with framework API adapters under `src/main/api`; API adapters should consume composed application services and transport mappers, not feature infra directly.
