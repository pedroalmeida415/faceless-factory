# Procedure-Aligned Use Cases

Accepted. Feature use cases are plain Effect programs under `src/features/<feature>/application/use-cases/`, and transport procedures should map 1:1 to those use-case names when the procedure only validates transport input, supplies caller context, maps typed failures, and runs the Effect at the edge. Do not wrap stable use cases in `Context.Tag` services or `*Live` layers unless the wrapper owns meaningful lifecycle, policy, resource management, or true implementation variation. Feature application ports live in capability-named files such as `store.ts`, `payment-gateway.ts`, or `events.ts`; avoid `ports.ts` catch-alls. Feature infra adapter files mirror the application port capability, such as `infra/store.ts`, and export concrete `*Live` Layer values. Transport imports application use cases, never feature infra adapters. Domain modules should be split by concept or invariant owner rather than catch-all `domain/<feature>.ts`, `types.ts`, `utils.ts`, or `schemas.ts` files. Deterministic in-memory domain rules should remain pure TypeScript functions; use Effect for use-case orchestration, I/O, resource lifecycle, concurrency, telemetry, and recoverable failures.
